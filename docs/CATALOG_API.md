# Location directory API v1

`GET https://rivianspotter.com/api/v1/catalog.json`

This public, read-only JSON endpoint is generated by `npm run build` from the same canonical location, charging, Roamer, and photo data used by the website. Both the regular Pages deployment and the scheduled data refresh publish it. No separate server, credentials, customer database, or app update is needed for directory changes after the client supporting this endpoint is installed.

## Contract

The response has `schemaVersion: 1` and `places: [...]`. Each place includes its stable `id`, `aliases`, directory categories, name, status, address, coordinates and precision, hours, source dates/URLs, photography metadata, related location IDs, and structured detail sections. `checkedOn` describes the source observation date, not the download time. Responses contain no visits, notes, bookmarks, or device locations.

`scripts/export-ios-catalog.cjs` owns the shared export. Public output is compact and deterministic, so unchanged source data produces identical bytes. Hosting-provided ETag and Last-Modified headers may be used for conditional requests. Clients must also work without these headers. A breaking schema change needs a new versioned path; preserve v1 for existing clients.

## App behavior

- Start immediately from the last validated cached response, falling back to the bundled catalog if no valid cache exists. If the bundled catalog is newer (by the latest `checkedOn` date), the old cache and its HTTP validators are discarded; a server response older than the bundled catalog doesn't replace it.
- Check on launch and foreground, at most once per 15 minutes per running app session. Pull-to-refresh in Browse, galleries, and Saved, or Settings → Location Updates → Check for Updates, bypasses the interval.
- Download over HTTPS with a 25-second request timeout. Validate the schema and records before accepting a response. Records are read individually so existing clients keep updating as the site grows: location types the client doesn't know are dropped from a record (a record left with none is skipped), out-of-range coordinates become "no pin", and unreadable records or records claiming an identity already taken are skipped. Reject payloads over 20 MiB, HTML/error responses, unsupported schemas, and any response where half or more of the records are unusable.
- Cache the catalog and HTTP validators in one atomic file. On failure retain existing data. Automatic checks fail quietly; the failure shows in Settings, and on browsing screens only after a manual refresh. A manual refresh during an automatic check waits for that check's result. Settings shows the last successful check; this is not a claim that every underlying source was checked then.
- Resolve saved places and currently open detail pages by canonical ID or aliases against the current catalog. A planned site becoming open immediately updates the Saved row and details after refresh. Directory updates never rewrite bookmarks, visit dates, or notes. Historical visit snapshots stay historical. A removed listing retains its saved snapshot until a matching listing returns; it is never silently deleted from the journal.

## Release

Deploy the website endpoint first and verify HTTP 200, JSON content type, and a valid v1 document. Then release an app build containing CatalogUpdates. Earlier TestFlight builds 1–4 do not fetch this endpoint. Regenerate the bundled offline fallback with `node scripts/export-ios-catalog.cjs` before app releases.

Local checks: `npm run test:ci`, `sh ios/Tools/test-core.sh`, and an Xcode simulator build. Tests cover conditional responses, offline/server/invalid-payload fallback, atomic-cache retention, corrupted-cache rejection, ID aliases, and saved planned-site updates without journal changes. Real two-device journal syncing is separate from this public API.

Server-side search, user accounts, and write endpoints can be added later if a product feature requires them. They are unnecessary for delivering this directory.
