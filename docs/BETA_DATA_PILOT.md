# Beta-only data publication pilot

This is an inactive pilot. It does not change live routing until the separate `beta-data` Amplify branch, its IAM scope, and a beta-only Cloudflare Worker route are deliberately provisioned. Production, Fastmail DNS, the existing beta shell, and the GitHub Pages fallback remain unchanged.

`beta-data-publish.yml` rebuilds the pinned beta template with a validated main data snapshot, checks the v1 catalog byte-for-byte against the corresponding production artifact, and publishes only data, generated location/directory/updates/stats pages, sitemap, three generated offline data scripts, a patched beta data loader, and the beta service worker. It does not include the map HTML shell, CSS, vendor, or imagery. An explicit manual run on main can seed the data branch while `BETA_DATA_PUBLISH_ENABLED` is absent. Once the beta route is proven, setting that variable to `true` switches the two existing release workflows from full beta deployments to this data-only deployment; production jobs do not change. Setting it back restores the prior full-beta workflow, but does **not** remove the Worker route.

The beta shell release is intentionally pinned to `2026.47.0-270f5b1dd20f`: it must match the deployed beta service worker before packaging. Generated pages use that stable shell release instead of a daily data digest. A deliberate shell redesign needs its own validated deployment, a corresponding pin and coordinated beta-data build. The beta data loader fetches a single JSON bundle, and the worker changes the loader and fallback data scripts to network-first while keeping the service-worker release stable. Existing installed workers initially have the old app.js cached under that same key: a real old-worker-to-new-worker activation test must prove the one-time replacement works before cutover. Local replay alone cannot prove that migration.

## Required hosting preflight

1. Using an authenticated AWS account, confirm the existing manually deployed Amplify app supports a separate `beta-data` branch. Create only that branch. The `RivSpotter-GitHub-Deploy` role needs narrowly scoped `amplify:CreateDeployment`, `StartDeployment`, and `GetJob` for that branch and required child ARNs, with the existing main-ref OIDC trust retained. Do not broaden access to production or expose credentials.
2. Merge the reviewed code to main with `BETA_DATA_PUBLISH_ENABLED` absent. Run **Publish beta data snapshot** manually on main. Its catalog comparison and deployment must succeed. Verify the data-origin catalog, HTML pages, aliases, sitemap and an unknown location's actual HTTP 404; validate `application/json`, conditional GET/ETag, and exact bytes. Check Amplify's app-wide rewrite rules do not rewrite missing pages into a 200.
3. Bundle `scripts/beta-data-worker.mjs` for Cloudflare Workers (for example with `npx esbuild --bundle --format=esm --platform=browser`) and deploy it without attaching a production route. Set `BETA_DATA_ORIGIN` to `https://beta-data.d3qy7654vf25z2.amplifyapp.com`. Attach a route scoped to `beta.rivspotter.com/*` only. The handler proxies only the fixed public data and generated-page paths and passes all other paths through to the existing beta origin. Confirm Cloudflare Full (strict) validates the current beta origin certificate.
4. Proxy only the existing **beta** DNS record through Cloudflare, preserving its existing target and all other DNS/email records. Verify HTTPS, map, charging details, new and alias deep links, missing routes, data-only paths, updates, SEO and sitemap, both catalog endpoints and service-worker upgrade in a real browser. Check network/cache behavior with the actual origin; never infer it from a local replay.
5. Enable `BETA_DATA_PUBLISH_ENABLED=true`. Follow a normal refresh through completion and compare beta catalog to the exact published production catalog. Keep the source scrape unchanged. Production and Pages stay on their existing full-release workflow.

## Recovery and limits

The data branch receives an Amplify deployment only after the archive and catalog have passed validation. Before cutover, verify how this app behaves on an interrupted or failed deployment and confirm its previous successful data version remains available. A failed build or failed deployment must not be acknowledged as a new data snapshot. Preserve prior Amplify deployments. An intentional catalog rollback must republish the prior content with a **newer** committed catalog revision; old revisions are rejected by installed iOS clients. Do not route to production as an automatic fallback for a missing beta location.

The patched loader fetches locations, charging and charging details in one bundle, avoiding mixed data between those three map inputs. Separate page navigations, the iOS catalog and the map can still straddle a deployment or cache boundary; no multi-request global atomicity is claimed. The Cloudflare route must not be enabled until the installed-worker migration and actual edge/cache behavior are tested.

Local snapshot replay: build the pinned design against two known committed `data/` versions; run `BETA_SHELL_RELEASE=2026.47.0-270f5b1dd20f node scripts/beta-data-snapshot.cjs DIST OUTPUT` for each; then `node scripts/replay-beta-data.cjs EARLIER OUTPUT`. These tests do not make any network requests to source providers or cloud hosting.
